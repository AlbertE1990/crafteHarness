# CraftAgent 开发与代码规范

> 文档类型：规范；状态：Accepted。

## 1. 适用范围

本规范适用于 `src/craft-agent` 及后续 ModelAdapter、Session、Agent Loop 和 Runtime 协议。
它用于保持公共 API、内部函数、注释和测试的可读性。已经稳定发布或存在外部调用方的 API 如需改变，必须
考虑兼容性；尚未发布的设计草案不保留无实际使用者的兼容层。

### 1.1 降低使用者心智负担

公共 API 的首要体验原则是：**能由框架根据已有信息确定性完成的工作，应优先在内部完成。** 普通使用路径
应让开发者只描述业务意图，不要求理解或串联内部适配步骤。

- 常规能力尽量从一个主要入口和一个配置根进入，避免调用方在多个 builder、registry 和 adapter 间跳转。
- 输入已经足够推导内部形式时，在配置边界完成 normalize、默认值、去重和冻结，不要求调用方预处理。
- 工具函数只在能表达新的业务选择时进入常规 API；纯粹为内部类型擦除或对象包装的函数应隐藏或降为高级入口。
- 文档先展示最短正确路径，再通过“高级用法”解释替换实现、底层协议和逃生口。
- 配置错误应在统一入口尽早报出，并使用业务字段名称；不能把内部转换失败变成调用方要理解的额外流程。
- 简化不能消除必要的显式意图：禁用、覆盖、整体替换和危险副作用仍必须由开发者清楚声明。
- 引入新公共概念前应先回答：框架是否已有足够信息代为完成？如果有，不新增调用步骤。
- 风险评估、交互传输和固定生命周期要分开：使用者只提供会改变业务决定的 `evaluate()`；审批 ID、
  pending Promise、超时、取消和重复提交等通用机制必须由 Agent 内收，不能要求每个 Runtime 重写 Broker。
- 同一语义优先只保留一种输入形式；项目未发布时直接删除被替代的包装、别名和识别分支。

例如，`defineTool()` 已包含 Schema、实现和策略，Agent 就应直接接受其结果并在内部转换为 `AgentTool`；
普通调用方不应为了注册再调用额外的转换或组装函数。

## 2. 函数参数排序

### 2.1 基本原则

参数按照“核心功能优先，辅助上下文靠后”排列，而不是按照调用者碰巧准备数据的顺序排列：

1. **主要操作对象**：函数真正读取、转换、验证或执行的数据。
2. **决定功能语义的参数**：模式、类型、目标、策略等会改变核心行为的必需参数。
3. **关联与诊断上下文**：名称、ID、日志标签和仅用于构造错误信息的字段。
4. **可选控制参数**：默认值、开关、回调和仅在部分路径使用的参数。

所有必需参数应位于可选参数和带默认值参数之前。这里的“使用频率”指参数参与核心算法的程度，
不是简单统计它在函数体内出现了几次。

### 2.2 当前示例

`assertClosedObjects()` 的排序为：

```ts
function assertClosedObjects(
  value: unknown,
  schemaName: 'inputSchema' | 'outputSchema',
  toolName: string,
  path: string = schemaName,
): void
```

原因：

| 参数         | 角色                | 排序依据                           |
| ------------ | ------------------- | ---------------------------------- |
| `value`      | 当前要检查的节点    | 主要操作对象                       |
| `schemaName` | Schema 语义和根路径 | 决定检查对象的语义，也提供默认路径 |
| `toolName`   | 工具诊断名称        | 不改变检查结果，只用于错误信息     |
| `path`       | 递归诊断路径        | 有默认值，只在递归和错误定位时使用 |

同理，重试校验函数使用：

```ts
function validateRetryPolicy(
  retry: ToolRetryPolicy,
  toolName: string,
): void
```

`retry` 是真正被校验的数据，`toolName` 只帮助生成错误信息。

### 2.3 参数过多时使用对象

当出现以下任一情况时，应优先使用命名参数对象：

- 参数超过三个且调用点难以看出含义。
- 多个连续参数类型相同，容易交换位置。
- 可选参数较多。
- 后续很可能增加关联字段。
- 参数共同表达一个稳定上下文。

不推荐：

```ts
executeAttempt(tool, input, 2, signal, 'run-1', 'session-1', true)
```

推荐：

```ts
executeAttempt(tool, input, {
  attempt: 2,
  signal,
  runId: 'run-1',
  sessionId: 'session-1',
  traceEnabled: true,
})
```

不要把所有参数机械地塞进一个对象。两个含义稳定且清晰的参数，例如 `toJsonSchema(schema, io)`，
保留位置参数更容易阅读。

### 2.4 回调与依赖注入

- 核心数据先于回调和观察器。
- 多个可注入依赖组成稳定运行上下文时，使用 `options` 或专门的 Context 类型。
- `AbortSignal`、Logger、Clock、随机数生成器等横切依赖，应通过上下文或 options 传入。
- 不使用隐藏的全局 service locator 获取网络、数据库、日志和会话依赖。

## 3. 命名与布尔值

- 函数名表达动作，例如 `validateRetryPolicy()`、`normalizeToolError()`。
- 布尔字段表达可回答的问题，例如 `idempotent`、`retryable`。
- 公共协议避免含义模糊的 `data`、`config`、`handler`；必须通过类型名或字段名限定语义。
- 多个布尔参数不得使用位置参数，应改为 options 对象或判别联合类型。

## 4. 注释规范

- 所有导出的类型、类、函数和公共方法必须有 JSDoc。
- 注释除了说明“做什么”，还应解释安全边界、不变量和“为什么”。
- 对无法由代码自动保证的声明，必须明确写出可信前提。
- 注册期检查要区分“配置形状正确”和“业务语义真实”。
- 未实现功能必须写明“规划中”，不能使用会让调用者误认为已经受保护的措辞。

例如，`idempotent: true` 应描述为“工具作者声明”，不能描述成“Harness 已证明该工具幂等”。

## 5. 错误与安全措辞

- `validate` 表示代码真正执行了验证，不用于无法证明的业务性质。
- `declare` 或“声明”用于工具作者提供、Runtime 尚未独立验证的元数据。
- `safe` 必须写明威胁模型；“可信代码中的低风险工具”不等于“可安全执行任意第三方代码”。
- 面向模型和前端的公开错误，与包含堆栈的服务端诊断日志必须分层。

详细威胁模型见[安全与信任模型](./security/trust-model.md)。

## 6. 状态与 Store 规范

- 核心状态优先记录不可变事实，不通过覆盖数组隐藏历史变化。
- append-only Store 的写入必须显式携带调用方观察到的版本。
- 批量追加必须全成或全败，不能在校验中途改变内部状态。
- ID、sequence 和 timestamp 由持久化边界分配，业务调用方只描述事件事实。
- 多页读取必须固定快照版本，不能在一次推导中混入并发新事件。
- 持久化输入必须复制；只写 readonly 类型不足以阻止外部对象引用修改历史。
- Store 接口不能暴露数据库驱动、ORM、HTTP 或前端展示类型。
- 派生函数遇到损坏顺序应直接失败，不能自动排序或静默修复。
- 事件 type 使用已经发生的事实命名，例如 `message.appended`、`turn.completed`。

详细行为见[Session Log 协议](./protocols/session-log.md)。

## 7. Agent Loop 状态机规范

- Run、Turn、Step、Tool Call 和 Attempt 必须使用准确术语，不能把所有循环层都称为“轮次”。
- 一次模型请求构成一个 Step；工具内部 retry attempt 不增加 Step。
- 模型调用前必须从 Session 固定快照推导消息并确认版本，不能使用跨 Run 的可变消息缓存作为事实源。
- 预算检查必须放在产生相应副作用之前；多 Tool Call 批次超限时全批拒绝，不能只执行前几个。
- assistant Tool Call 意图成功写入后，应为每个 callId 形成对应 tool message；取消也要保持模型消息配对完整。
- `completed`、`stopped` 和 `failed` 必须分开建模；预算耗尽不伪装成模型或基础设施异常。
- Session 版本冲突不得静默合并，也不得在缺少恢复协议时自动重放模型和工具。
- 实时事件观察器属于旁路；观察器故障不能更改执行结果，后续由 DiagnosticSink 记录其异常。
- 并行、重试和恢复不能只通过 `Promise.all` 或外层循环临时加入，必须先定义提交、取消、计费和副作用语义。

详细行为见[Agent Loop 协议](./protocols/agent-loop.md)。

## 8. 变更检查清单

### 8.1 Agent 配置与门面

- 公共构造配置使用单一对象参数；新增模型、Store 或策略选项不得制造第二个配置根。
- `defineAgentConfig()` 只归一化显式输入，不读取环境变量或全局配置。
- 门面可以提供官方 Adapter 的便利创建，但 contracts/core/sessions/tools 不得反向依赖 Adapter。
- 默认依赖必须可替换；时钟和 ID 生成器保留测试注入点。
- 应用输出与完整轨迹使用不同类型和回调，不能为了前端方便删减底层 AgentEvent。
- Session 列表来自 Store 能力，不在 Runtime 维护第二份会话 ID 索引。
- 配置结构可以冻结，但不得擅自深度冻结调用方注入的有状态 Adapter、Store 或策略实例。
- 集合查询默认返回满足列表展示所需的最小摘要；大体积详情通过 ID 按需读取，禁止在列表内部形成 N+1 查询。
- 面向应用的详情投影不能为了方便而丢弃已有的关联信息；消息内容与 `turnId/sequence/timestamp` 等上下文应分层保留。

新增或修改函数时检查：

- 主要操作对象是否排在最前？
- 影响功能语义的必需参数是否排在诊断参数之前？
- 可选参数和默认参数是否位于末尾？
- 三个以上参数是否更适合组成命名对象？
- 同类型位置参数是否容易被调换？
- 注释是否准确区分“已验证”和“由开发者声明”？
- 公共 API 调整是否考虑兼容性和迁移说明？
- 测试是否覆盖参数顺序调整后的所有调用点？
- 状态写入是否保持原子追加和版本检查？
- 分页读取是否来自同一个固定快照？
- 持久化对象是否与调用方原始引用隔离？
- 新循环是否有显式预算、取消检查和封闭停止原因？
- 工具调用意图与每个 tool result 是否保持协议配对？
- 实时事件与持久化 Session 事实是否仍然分层？
- 并发冲突是否会阻止基于旧上下文的结果写入？
